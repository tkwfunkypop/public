# PR Babysit Skill

GitHubのPRを継続的に見守るときの標準手順。単発の確認で終わらせず、**マージまたはクローズされるまでが1つのタスク**として扱う。

## 1. 開始時（購読直後）にやること

- `subscribe_pr_activity` で対象PRを購読する。
- 購読して終わりにしない。即座に現状を一巡チェックする:
  - `mcp__github__pull_request_read`（`method: get`）でPR全体の状態（open/draft/mergeable_state）
  - `method: get_check_runs` でCI状況
  - `method: get_review_comments` で未解決レビュースレッド
  - `method: get_comments` で一般コメント
- 何も無ければその旨を短く報告し、監視を継続する。

## 2. イベントが来たときのトリアージ

`<github-webhook-activity>` でCI失敗・レビューコメントが届いたら、以下の3択で判断する。

| 判断 | 条件 | アクション |
|---|---|---|
| **直す** | 修正方針に自信があり、変更が小さく、会話の流れと矛盾しない | 修正してpush → チェックリスト更新。逐一報告せず、解決した/質問がある時だけ返信 |
| **確認する** | レビュアーの指摘が複数解釈可能、アーキテクチャ上重要な変更を伴う | `AskUserQuestion` で必ず確認してから動く。答えられるだけの文脈を質問に含める |
| **スキップする** | 重複、対応不要と判断できる | 何も言わずスキップ（サイレント） |

例外: タスクが「CIを通す」「マージ可能にする」「グリーンになるまで面倒を見て」など**CIを通すこと自体が目的**の場合、CIイベントに対して3で終わらせない。失敗のたびに再診断→再対応（rebase、再実行、修正push）を繰り返す。一回直して終わりにしない。CIがグリーンになったら、それ自体を成果として報告する（サイレントスキップしない）。

## 3. Webhookが拾えないものを補う

Webhookイベントは以下を配信しない:
- CI成功
- 新しいpush
- マージコンフリクトへの遷移

これを補うため、`send_later`（利用可能な場合）または `CronCreate`（1回限り・`recurring: false`）で **約1時間後** に自己チェックインを予約する。

- チェックイン時にやること: PRの状態・CI・レビューコメント・マージ可否を再取得する。
- 何も変化がなければ、**ユーザーには何も言わずに**次の1時間後チェックインを再予約する（サイレント再アーム）。
- 何か動きがあれば、セクション2のトリアージに従って対応する。
- `CronCreate` は分単位を `:00`/`:30` からずらして予約する（例: `23 0 13 7 *`）。

## 4. 終了条件

- PRが **マージ** または **クローズ** されたら、監視ループを終了する。
  - `unsubscribe_pr_activity` を呼ぶ
  - 以後の再チェックイン予約は行わない
  - 最終状態をユーザーに報告する
- ユーザーから「もう見なくていい」「監視やめて」と言われたら、即座に:
  - `unsubscribe_pr_activity` を呼ぶ
  - そのPRへの追加pushを止める
  - それ以降そのPRについて何もしない

## 5. 一度に複数PRを見るとき

PRごとに独立して`subscribe_pr_activity`し、チェックリストやチェックインもPR単位で管理する。1つのPRの状態を別PRの判断に混ぜない。
